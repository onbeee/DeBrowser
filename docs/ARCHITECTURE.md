# DeBrowser 架构

本文档说明 DeBrowser 当前的系统架构、模块职责与运行机制。数据库结构见 [DATABASE.md](DATABASE.md)，阶段状态见 [ROADMAP.md](ROADMAP.md)，开发流程见 [DEVELOPMENT.md](DEVELOPMENT.md)。

## 架构概览

DeBrowser 是模块化单体：一个 Go 二进制内嵌一个 React 前端，通过 Wails v3 以原生 Windows 桌面应用交付。没有微服务，没有外部服务器，全部状态保存在用户自己的机器上。

```text
┌────────────────────────────────────────────────────────┐
│ React 前端 (frontend/)                                 │
│  八个页面 · 布局组件 · Zustand 界面 store              │
└──────────────┬─────────────────────────────────────────┘
               │ 生成的 bindings + 类型化事件 (app:status)
┌──────────────▼─────────────────────────────────────────┐
│ Wails v3 应用 (internal/app)                           │
├────────────────────────────────────────────────────────┤
│ 服务层 (internal/service)                              │
│  AppService · InstanceService · BrowserService         │
│  DiagnosticsService                                    │
├────────────────────────────────────────────────────────┤
│ 基础层 (internal/)                                     │
│  paths · config · settings · logging · database        │
│  model · store · runner · secrets · singleinstance     │
│  pfiles · safedelete · lifecycle · version             │
├────────────────────────────────────────────────────────┤
│ 本地资源（便携目录，见「数据目录」）                   │
│  data/debrowser.db · data/profiles/ · data/logs/       │
│  data/secrets.vault · config/settings.json             │
└────────────────────────────────────────────────────────┘
```

职责划分（AGENTS.md）：Go 负责浏览器进程管理、实例生命周期、Profile 隔离、浏览器登记、书签数据、数据库与日志；React 只负责渲染、交互、表单、表格、前端状态与通知。

## 技术栈

Go 1.26 + Wails v3.0.0 后端；React 18 + TypeScript + Vite + Tailwind CSS v4 前端；SQLite（modernc.org/sqlite，纯 Go 驱动）存储。版本明细见 [README.md](../README.md) 的技术栈表。

| `internal/logging` | 统一自动记录系统 |
| `internal/secrets` | 凭据 Vault（历史凭据兼容保留） |

| `internal/config`、`internal/settings` | 配置解析与用户设置（`config/settings.json`） |

| `internal/pfiles`、`internal/safedelete` | Profile 文件夹的对象锚定安全删除 |

| `frontend/bindings` | Wails 生成的 TypeScript bindings，永不手工编辑 |

## 启动顺序

`main.go` 的启动顺序固定：

1. `paths`/`config` 从可执行文件所在目录解析便携布局，创建全部目录并探测可写性；不可写时明确报错中止，永不回退到 `%AppData%`。启动是直接的：没有欢迎页或选择页，也不从任何其他位置扫描、检测或导入数据。
2. `logging` 打开日志系统（在数据库与服务之前打开，关闭时最后关闭）。
3. `singleinstance` 取得按安装划分的操作系统级文件锁（`data/app.lock`）。锁由操作系统仲裁并在持有者以任何方式退出时自动释放，不存在陈旧锁；第二次启动只写入激活信号（`data/activate.request`）请已运行实例聚焦窗口，然后在不触碰数据库的情况下退出。
4. `database` 打开 SQLite 并以事务方式应用待执行迁移（升级前先做经验证的备份，见 [DATABASE.md](DATABASE.md)）；`secrets` 打开凭据 Vault。
5. `service` 构建六个服务并完成启动对账（见「浏览器运行机制」）；`app` 组装 Wails 应用并运行。后台循环（状态事件、激活监视）由 `lifecycle` 在应用 context 下治理，关闭时按固定顺序释放：循环 → 数据库 → 实例锁 → 日志。

## 前后端通信

- **Bindings**：六个 Go 服务的导出方法经静态生成的 TypeScript bindings 暴露给前端（`wails3 generate bindings` 重新生成；CI 校验已提交的 bindings 与生成结果一致）。当前共 6 个服务、45 个方法。前端只能调用明确注册的服务方法，不能执行任意命令。
- **事件**：目前只有一个类型化事件 `app:status`（应用状态，每 10 秒发出，也可经 `AppService.GetStatus()` 按需获取）。
- **前端状态**：单个 Zustand store 保存当前页面、后端状态与主题；页面级状态留在各页面内。每次用户操作由前端生成唯一的 `operation_id` 并作为绑定的第一个参数传入，贯穿该操作的全部日志记录（见「日志」）。

## 浏览器运行机制

### 浏览器登记

手动登记是**纯路径登记**：用户在文件选择器中任选一个程序可执行文件，`BrowserService` 只把绝对路径与从文件名派生的显示名存入 `external_browsers`。不做任何身份、产品、版本、签名、发布者或存在性检查，不要求是 Chrome 或 Brave；登记本身永不启动、复制、移动、修改或删除该程序，永不读取它的 Profile。同一路径重复登记返回既有记录；移除登记只删除数据库行，被实例引用的登记禁止移除（不级联影响实例）。

### 实例与实例文件

每个实例绑定一个实例文件：`data/profiles/` 下的文件夹，浏览器以它为 `--user-data-dir` 运行。一对一绑定由数据库 UNIQUE 约束与服务检查共同保证，运行中的实例之间永不共享。

- 新建：默认（持久计数器顺序编号 P-1、P-2……，只增不减、永不复用）、自定（新建文件夹）、选择（绑定保留的未绑定文件夹，不复制内容）。
- 编辑：重命名当前文件夹（数据随文件夹移动），或更换绑定（原文件夹解除绑定并保留在磁盘上）。
- 删除实例默认只删除数据库记录、保留实例文件；只有用户明确选择「删除实例及实例文件」时才删除文件夹（见「安全与数据保护」）。

### 启动、关闭与进程身份

- **启动**：服务按实例关联的登记 ID 实时解析可执行路径（路径不落库，登记改路径即时生效），校验实例文件是 `data/profiles/` 下的受管文件夹（缺失时补建空目录；无法证明位于受管根内时拒绝启动），以 `--user-data-dir=<实例文件绝对路径>` 启动进程，并附带 `--remote-debugging-address=127.0.0.1` 与 `--remote-debugging-port=<每实例独立分配的端口>`（Stage 10 的 CDP 接入；端口仅绑定回环地址，分配方式与生命周期见「同步机制」）。身份核验只比对 `--user-data-dir`，不受调试参数影响。进程存活过稳定窗口且身份核验全部通过后，才写入身份记录（`instance_runtime` 表）、置为运行中并开始监控。
- **身份核验**：PID + 进程创建时间 + 可执行路径 + 命令行，四项共同核验；命令行经严格参数解析，`--user-data-dir` 的值必须与实例文件完整路径精确相等（子串或前缀相同不算一致）。任一信号缺失或不可读一律视为核验失败，绝不猜测。
- **关闭**：只对已核验的被跟踪进程投递优雅关闭（Windows 的 `WM_CLOSE`，等同用户点击关闭按钮）；从不按进程名全局结束进程，从不强制结束进程树。限定时间内未退出则如实报告「关闭未完成」，实例保持运行中。
- **退出感知**：每个被跟踪进程都有监控协程；用户直接关闭浏览器窗口或浏览器崩溃都会被感知，身份记录随之删除，状态按退出码更新为已关闭或错误。
- **重启恢复**：DeBrowser 退出不关闭浏览器。下次启动时按身份记录逐项重新核验：通过的重新接管监控；证明已失效的清除并置为已关闭；进程仍在但身份无法确认的，实例进入「无法确认」状态并冻结一切可能危及数据的操作（启动、关闭、删除、重命名/更换实例文件），只保留无风险的查看与名称、内核关联修改，留待后续对账重新判定。核验失败且无法确认本次启动的进程已退出时，同样写入身份记录进入「无法确认」，绝不冒充普通失败。

## 书签机制

书签有两套完全独立的数据：DeBrowser 资源库（SQLite `bookmark_nodes` 树，见 [DATABASE.md](DATABASE.md)）与各实例 Profile 根目录下的 Chromium 原生 `Bookmarks` 文件。资源库的编辑、删除不自动影响任何实例；实例书签的修改不回写资源库。

- **文件读写**：`internal/chromebookmarks` 把 `Bookmarks` 文档作为解码后的 JSON 结构整体处理，完整保留根节点、节点 ID/GUID、时间字段与未知字段；数字以原始文本精度保留。书签文件不存在、格式无法确认、无法解析或结构不符合 Chromium 书签格式时明确报错：文件不存在不视为「书签为 0」，也不为无法确认的 Profile 创建书签文件；绝不猜测其他浏览器的数据格式（不支持 Firefox 等非 Chromium 书签存储）。不读取、不检查用户登记的浏览器 EXE，兼容性只由 Profile 内书签文件本身判定。
- **运行状态保护**：读写任何实例的书签文件之前，必须经运行时生效状态确认该实例已停止（不只看数据库落库状态）；运行中与无法确认状态一律禁止读写，批量操作逐实例独立判定、跳过并反馈原因。书签管理页面的「同步」入口会先检查全部实例：存在运行中实例时，由用户确认后调用既有正常关闭流程关闭全部实例并复查确认停止，才打开同步弹窗；后端在每次实际读写前仍独立复核目标实例状态。DeBrowser 不自动关闭或重启浏览器来迁就书签操作——关闭只发生在用户在同步入口明确确认时。
- **写入安全**：同一 Profile 的书签操作互斥串行；写入走同目录临时文件 → 校验 → 原子替换 → 重新读取并完整验证；替换前把原文件保存为单个滚动恢复副本 `Bookmarks.debwbak`（恢复副本本身也经临时文件加原子替换写入，不无限堆积）。替换后验证失败时自动用恢复副本还原原文件，并区分「已恢复」与「恢复失败」如实报错；任何失败都不假报成功。
- **分发规则**：同步把资源库所选节点（文件夹含全部子树、保留层级）写入目标实例的书签栏；同一目标文件夹内 URL 相同视为已存在并跳过，同名文件夹复用不重建。
- **聚合搜索**：同步弹窗的编辑/删除先跨实例聚合搜索（只查已确认停止且可读的实例），结果只呈现名称、网址与不同实例数量，不暴露实例名称或明细；精确目标（实例、根节点、节点 ID、父级路径与内容快照）只保存在后端短期会话中，执行时重新核对实例状态、重新读取文件并按节点 ID 与路径复核后才修改。

## 同步机制

多开同步（Stage 10，含原 Stage 9C 未完成的 CDP 接入）：用户指定一个主实例与若干跟随实例，只操作主实例，操作同步到全部跟随实例。同步只传递用户操作，绝不读取或共享任何实例的 Profile 数据（Cookie、密码、历史、网页内容均不采集；统一日志只记同步会话的生命周期操作，不记录输入内容与坐标轨迹）。

- **CDP 生命周期**：每个实例启动时分配一个独立的回环端口（短暂监听 `127.0.0.1:0` 取空闲端口后释放给浏览器绑定），随进程监控保存于内存；实例停止或进程退出即失效，不落库。DeBrowser 重启后重新接管的实例是旧版本启动的进程、没有调试端口，明确标记为「暂不支持同步」，用户关闭并重新启动该实例后即可参与。同步开始前逐实例重新核验运行状态并实际建立 CDP 连接、校验浏览器版本与页面附加，任一条件不满足则整场不启动、如实报错；非 Chromium 内核（无法提供 CDP）由此被识别为不支持，不伪造支持状态。`internal/cdp` 是最小客户端（浏览器级 WebSocket + flatten 目标会话），只实现本功能用到的 Target / Input / Page / Browser 命令，不引入浏览器自动化框架。
- **网页内部操作**：经各实例自己的 CDP 连接以 Input 域分发（鼠标移动/按下/释放/滚轮、键盘、文本），坐标按主/跟随各自的内容区矩形与 CSS 视口比例映射，不假设窗口尺寸一致。标签的新建、关闭随主实例的 Target 生命周期事件镜像；地址栏导航与前进/后退经目标 URL 变化镜像为跟随实例的页面导航。主实例连接断开即整场停止并提示；单个跟随实例失败只标记该实例，其余继续。
- **浏览器自身界面操作**：地址栏、标签栏、菜单、扩展弹窗等浏览器界面不属于网页内容，使用 Windows 低级钩子捕获主实例窗口树内的真实输入，按窗口矩形相对位置映射后，以 `SendInput` 注入跟随实例的对应窗口（注入前短暂激活目标窗口、完成后恢复主实例焦点；注入事件带专用标记，捕获侧直接丢弃，不会循环镜像）。弹出窗口按其所属进程与窗口归属对应到同一实例。捕获到的输入先按命中点分类：落在网页内容区（Chromium 渲染子窗口）的走 CDP 通道，其余走原生通道；键盘输入按最近一次点击确立的焦点区域分类。此机制依赖真实 Windows 桌面行为（焦点切换、输入法组合等），其可靠性以 Windows 11 实机验收为准，未验收前不视为已验证能力；中文输入法在网页输入框中的组合文本不经虚拟键码传递，原生通道中由各跟随实例自身的输入法按相同按键序列组合，实际一致性同样待实机验证。
- **窗口排列**：用户可对任意运行中实例一键网格排列（按所选显示器的工作区计算，主实例在首位，窗口不超出工作区，最小化/最大化窗口先还原再定位）；排列前的窗口矩形只保存在内存中，「恢复窗口」按此还原，不写入数据库。排列与恢复不依赖同步会话是否开启。
- **会话状态**：同步会话仅存于内存（主实例、跟随实例、生命周期状态与每跟随实例的失败标记），暂停时停止分发并释放已按下的键鼠状态，停止时释放输入状态、关闭全部 CDP 连接并清理临时状态；不因暂停或停止同步关闭浏览器或修改 Profile。

## 安全与数据保护

- **Profile 隔离**：实例文件互不共享；活动 Profile 永不在浏览器使用期间被复制。DeBrowser 不宣称指纹隔离。
- **实例文件删除保护**：「删除实例及实例文件」是显式破坏性路径：拒绝删除运行中的实例、拒绝 profiles 根目录本身、拒绝任何无法证明严格位于 `data/profiles/` 内的目标（符号链接与每个路径组件都必须解析到受管根内）。删除以经验证的文件系统**对象**为锚（`internal/pfiles` 先移入隔离槽、数据库记录删除成功后才由 `internal/safedelete` 擦除），不以路径字符串做裸递归删除；平台无法提供对象锚定保证时失败关闭（拒绝并保留数据）。
- **进程操作边界**：只操作 DeBrowser 自己启动并核验过的进程；身份无法确认时宁可冻结，也不误关、误删。
- **凭据 Vault（兼容保留）**：`internal/secrets` 保存已移除的代理/订阅功能写入的历史凭据（`data/secrets.vault`，Windows DPAPI CurrentUser 保护；SQLite 只存不透明 `secret_ref`，明文永不进入数据库、日志与设置）。当前没有任何功能创建新凭据，但 Vault 在启动时照常打开：条目在仍被历史行引用时永不回收，删除只有「未被引用才删」的受守卫形式，没有无条件删除。DPAPI 的跨机器限制见 [README.md](../README.md)。

## 日志

统一自动记录系统（`internal/logging`）是唯一的记录系统，不存在独立的操作审计或诊断导出模块。三条 JSONL 流存放在 `data/logs/`（按日期命名、5 MB 分卷）：

- **运行记录**（保留 30 天）：应用生命周期、页面打开/离开、后台循环与结构化运行日志。
- **操作记录**（保留 90 天）：用户发起的业务操作及其步骤与结果。
- **错误记录**（保留 90 天）：错误级日志与每次失败操作的完整错误事件（含用户实际看到的提示）。

记录采用统一事件模型，以 `operation_id` 关联一次操作的全部事件。三条流共用一个用户可配置的总容量上限（默认 100 MB，存 `config/settings.json`），超出时先整文件删除最旧的已轮转文件，再按完整操作组修剪当前文件，最新一条记录永不删除。记录落盘前统一清洗：凭据类字段整体丢弃，自由文本脱敏；写入失败只累计计数，永不使业务操作失败。数据管理页可按类别与日期范围导出 ZIP（逐文件 SHA-256 清单、导出前敏感性扫描、命中即中止、路径脱敏），供用户把日志提供给开发者定位问题。
