# DeBrowser Architecture

## Overview

DeBrowser is a modular monolith: one Go binary embedding a React frontend, shipped as a native Windows desktop application through Wails v3. There are no microservices and no external servers — all state lives on the user's machine.

```text
┌────────────────────────────────────────────────────────┐
│ React frontend (frontend/)                             │
│  pages · layout components · Zustand UI store          │
└──────────────┬──────────────────────┬──────────────────┘
               │ generated bindings   │ typed events
               │ (frontend/bindings)  │ (app:status, …)
┌──────────────▼──────────────────────▼──────────────────┐
│ Wails v3 application (internal/app)                    │
│  services registered with the application object       │
├────────────────────────────────────────────────────────┤
│ Services (internal/service)                            │
│  AppService · InstanceService · DiagnosticsService     │
│  BrowserService (Stage 9A; bookmark wiring in Stage 9C) │
├────────────────────────────────────────────────────────┤
│ Foundation (internal/)                                 │
│  paths · config · settings · logging                   │
│  database (SQLite + migrations + backups) · version    │
│  model · store (repositories, Stage 2)                 │
│  version                                               │
├────────────────────────────────────────────────────────┤
│ Local resources                                        │
│  <root>\data\debrowser.db (portable layout)      │
│  <root>\data\profiles\<instance-id>\  (Stage 3)│
│  <root>\webview2-data\  (app window WebView2 data)    │
│  Chromium processes over CDP                  (Stage 9)│
└────────────────────────────────────────────────────────┘
```

## Backend (Go)

`main.go` is the entry point. Startup order is fixed:

1. `internal/config` + `internal/paths` resolve the portable layout from the executable's directory (never the working directory), create all directories and probe that the application root is writable - a read-only location aborts startup with a clear error; there is no fallback to `%APPDATA%`. Startup is direct: a first launch creates and initializes the same directories and files an existing installation already has — there is no welcome or choice page.
2. `internal/logging` opens the categorized structured logs under `data/logs` (Stage 5B, see "Logging and diagnostics" below) — before the database and services, and it is closed last on shutdown.
2b. `internal/singleinstance` takes the per-installation lock `data/app.lock` (Stage 3) as an operating-system file lock — `flock` on Unix, `LockFileEx` on Windows. The OS is the only arbiter: exactly one process can hold it, contenders never delete or recreate each other's lock file (no check-then-delete race), and the lock is released by the OS itself when the holder exits for any reason (clean exit, crash, force kill, power loss), so stale locks cannot exist. The file records the holder's PID for information only. A second launch of the same portable folder gets AlreadyRunning, writes an activation signal (`data/activate.request`) asking the running instance to focus its window, and exits without touching the database. Other portable folders use other lock files and are unaffected.
3. There is no external data migration step: DeBrowser never scans, detects or imports data from `%APPDATA%`, `%LOCALAPPDATA%` or any other location. The Stage 1 Roaming auto-migration (`internal/migration`) was removed in Stage 5A; the only migrations that exist are the in-database SQLite schema migrations of step 4.
4. `internal/database` opens SQLite (WAL mode, `synchronous=FULL`, foreign keys on) and applies pending migrations transactionally, taking a verified `VACUUM INTO` backup into `data\backups\` first when upgrading an existing database. Core data access goes through `internal/store` repositories over `internal/model` types (Stage 2).
5. `internal/service` constructs the Wails services (including persisted user settings from `config/settings.json`, managed by `internal/settings`).
6. `internal/app` assembles the Wails application (services, main window with `Windows.WebviewUserDataPath` set to the portable WebView2 directory) and `main` runs it. Background loops (10s status events, 500ms activation watcher) run under an application context via `internal/lifecycle`; shutdown cancels the context and `App.Run` waits for the loops to drain before returning — the wait is unbounded by design (a warning is logged every 5s), because cancelling a context cannot interrupt a callback already running, and returning early would let `main` close the database underneath a live reader. Only once every loop has provably exited does `main` close the database, release the instance lock and close the log — in that order. `main` is a thin wrapper over `run() error`; nothing calls `log.Fatalf` mid-startup, so deferred cleanup always runs.

Stage 3 also adds `InstanceService` (bindings: `ListInstances`, `GetInstance`, `CreateInstance`, `UpdateInstance`, `DeleteInstance`, `DeleteInstanceAndProfile` — a `ListProxies` binding added in Stage 4A was removed again in the PR #9 cleanup) over the Stage 2 store: validated instance metadata CRUD with Chinese, user-facing constraint messages. `DeleteInstance` removes metadata only and never touches profile files; `DeleteInstanceAndProfile` is the explicit destructive path and refuses persisted-running instances, the profiles root itself, and anything that cannot be PROVEN to stay inside `data/profiles` by real-path resolution: the target itself must not be a symlink/reparse point, and every path component must resolve (intermediate symlinks and Windows junctions included; `GetFinalPathNameByHandle` on Windows, `EvalSymlinks` on Unix) to a location still strictly inside the resolved profiles directory. Deletion is then failure-atomic and OBJECT-anchored rather than a bare recursive remove (`internal/pfiles`): the move into a quarantine slot under `profiles/` acts on the verified filesystem object, never on the verified path string — on Linux the descent from the profiles root is anchored to directory file descriptors (`openat` with `O_NOFOLLOW` at every component, the root itself opened `O_NOFOLLOW`) and the move is `renameat2(RENAME_NOREPLACE)` between the two pinned fds, with a post-move `(dev, ino)` identity check; on Windows the target directory is opened with `FILE_FLAG_OPEN_REPARSE_POINT`, its identity is verified through the handle (reparse attributes plus `GetFinalPathNameByHandle` against the verified parent), and the rename itself is performed through that handle (`SetFileInformationByHandle`/`FileRenameInfo`, no-replace), so swapping any path component after verification cannot redirect the move. The database record is deleted next; on failure the object is moved back through the same anchor (on Windows the restore first re-verifies the original parent's identity and refuses, leaving the data in quarantine, if the parent now resolves elsewhere), and only with the record gone is the quarantine tree wiped by `internal/safedelete`, with the object identity chain unbroken from verification to deletion: the verified handle is NOT closed before the wipe — on Linux the wipe runs as `RemoveVerifiedAt` relative to the pinned profiles-root fd (the quarantine slot must still hold the exact `(dev, ino)` object verified at move time, and every entry's identity is re-verified immediately before it is unlinked), and on Windows the very handle that was verified and renamed is handed to the wipe engine, which enumerates children FROM directory handles (`GetFileInformationByHandleEx` with the extended directory classes `FileIdExtdDirectoryRestartInfo`/`FileIdExtdDirectoryInfo` — the documented Win32 `FILE_INFO_BY_HANDLE_CLASS` family — yielding per-child 128-bit file IDs), opens each child RELATIVE to its verified parent handle (`NtCreateFile` `RootDirectory`, deliberately WITHOUT `FILE_SHARE_DELETE`, so an opened object cannot be renamed out of the tree by another process while the wipe holds it), requires the opened child's 128-bit identity (volume serial plus `FileId` from `FileIdInfo`) to equal its enumerated identity (a swap between enumeration and open aborts the wipe; a filesystem that cannot provide the extended classes or a 128-bit identity fails the wipe closed rather than degrading the check; the identity guarantee is contemporaneous rather than a permanent object credential — Microsoft documents that file IDs may be reused after an object is deleted, while on NTFS an object keeps its ID until deletion — so the comparison binds only the enumerate→open window, which the share modes then close), and deletes through the verified handles (`FileDispositionInfo`), reparse points as link objects only. Linux guarantee boundary: descriptor-anchored deletion follows verified inodes and re-verifies identity before every unlink, so an object that was never verified inside the boundary can never be deleted — but Linux has no share modes, so a same-UID process that can rename entries inside the tree can move a verified object out mid-wipe and deletion follows that object; this residual requires a hostile same-UID process with write access inside the profile tree and is outside the single-user desktop threat model (Windows closes it via share modes). No path string is re-resolved at any depth on either platform, so replacing the profiles root or any intermediate path during the wipe cannot redirect the deletion. On Darwin the standard library offers no descriptor-relative or handle-based rename, so the destructive operation fails closed (refused, data and record intact) rather than falling back to a path-based move. There is no process manager yet, so at startup any instance still persisted as `running` is reconciled to `stopped` (`Store.ReconcileInstanceStatuses`) — with the single-instance lock, such a row can only be a leftover of a dead process. No schema migration was needed for Stage 3.

Ownership rules from AGENTS.md: Go owns browser process management, instance lifecycle, profile isolation, kernel management, bookmarks, synchronization, database operations and backup/recovery. React owns rendering, interaction, forms, tables, frontend state and notifications only. Proxy management is **not** a current responsibility: it was removed from the product scope in the PR #9 cleanup (see "Removed proxy / subscription / Mihomo features" below); the historical proxy database structures and the vault reference queries remain as compatibility facilities only.

### Frontend ↔ backend communication

- **Bindings**: exported methods on registered Go services are exposed through statically generated TypeScript bindings in `frontend/bindings/` (regenerate with `wails3 generate bindings`; never edit by hand).
- **Events**: typed custom events registered in `main.go` (`application.RegisterEvent`). Stage 1 defines one event: `app:status` carrying `service.Status`, emitted every 10 seconds and on demand through `AppService.GetStatus()`.

## Frontend (React)

- `src/components/layout/` — sidebar navigation, top toolbar, bottom status bar.
- `src/components/` — shared layout components (sidebar, top bar, status bar). There is no console panel.
- `src/pages/` — one page per navigation entry. Modules not yet delivered render an explicit "planned for Stage N" state instead of fake data.
- `src/stores/` — Zustand store for UI state (current page, backend status, theme, session log lines).
- Styling is Tailwind CSS v4 through the `@tailwindcss/vite` plugin (`src/index.css`).

## Browser discovery and kernel management (Stage 9A)

Stage 9A adds `BrowserService` (bindings: `DetectSystemBrowsers`, `RedetectBrowsers`, `ListBrowsers`, `GetBrowserDetails`, `AddBrowserManually`, `GetOfficialStableVersion`, `InstallManagedKernel`, `ListManagedKernels`, `VerifyManagedKernel`, `DeleteManagedKernel`) over two new packages:

- `internal/browserprobe` detects browsers the user already has installed — Google Chrome Stable and Brave Stable on Windows 11 x64 — from regular system information only: registry App Paths, registry uninstall records and the well-known install directories, for both per-user and machine-wide installs, deduplicated by canonical path. The disk is never scanned and no detected executable is ever launched during detection. A candidate is only reported as a verified browser after its version resource identifies the product and its Authenticode signature verifies against the expected publisher (Google LLC / Brave Software, Inc.); a file merely named chrome.exe proves nothing, and signature absence, invalidity or publisher mismatch yields an explicit verification-failed record. Detection results are runtime data: they are never written to the database, and DeBrowser never copies, modifies, uninstalls or deletes a system browser or reads its everyday profile. Manual registration (native file picker) runs the identical verification and is held in memory for the session only.
- `internal/kernels` manages DeBrowser's own optional Chromium builds from the official Chrome for Testing Stable metadata. The metadata endpoint is a fixed constant; downloads are accepted only over HTTPS from Google's official hosts with every redirect hop re-validated, and there is no user-supplied URL anywhere. The official metadata publishes no SHA-256 for these builds, so integrity rests on HTTPS + host whitelist + bounded, path-safe ZIP extraction (file-count/size caps, no absolute or `..` entries, no symlinks) + extracted `chrome.exe` version match + Authenticode verification (Google LLC) — no hash check is claimed that does not exist. Installation is atomic (temp directory on the same volume, renamed into `kernels/<version>` only after every check passes; failures clean up). Only managed kernels are persisted (migration 0010, relative portable paths, unique per version+platform); deletion resolves and re-validates the real directory strictly inside the kernels root before removing files and then the row, marking the row `missing` if the row delete fails after the files are gone. Install progress is reported to the frontend on the typed `kernel:install-progress` event.

Stage 9A launches no browser process; real start/stop, profile creation and CDP arrive in Stage 9B.

## Browser isolation (foundations in Stage 3, runtime in Stage 9)

Stage 3 delivered the foundations only: instance metadata management, the independent profile directory layout under `profiles/` (one directory per instance ID), and the profile-deletion safety mechanism described above. Stage 3 does NOT implement Chromium process management or actually launching a browser — there is no process manager yet.

Stage 9 adds the runtime: browser kernel management, managed Chromium processes, instance start/stop, CDP wiring, independent browser configuration and runtime isolation. In that final form, every browser instance has a unique ID, an independent user data directory under `profiles/`, an independent configuration and its own managed Chromium process. A user data directory is never shared between running instances, and a live profile is never copied while Chromium is using it. DeBrowser does not claim fingerprint isolation unless it is explicitly implemented and tested.

## Credential storage (Stage 4A, internal/secrets)

The credential vault holds the credentials written by the removed proxy/subscription features (proxy credentials and subscription URLs) in one encrypted vault file, `data/secrets.vault` (`paths.Layout.SecretsFile`). SQLite holds only the opaque `secret_ref`; plaintext never reaches the database, logs, settings files or frontend persistent state. No current feature creates new credentials, but the vault, its entries and its reference protection are fully retained — historical credentials must stay resolvable and must never be collected while a historical row still references them — and `main` still opens the vault at startup exactly as before (see the scope note below).

- **Encryption**: Windows DPAPI (CurrentUser) in production. DPAPI binds decryption to the same Windows user on the same machine: moving the portable folder on one machine keeps working; another machine or user makes entries undecryptable, which the store reports per entry (`ErrCorrupt`) so the UI can ask for re-entry — entries are retained, never silently dropped or downgraded to "no credential". Unix builds use an AES-256-GCM keyfile protector as a development stand-in only.
- **Consistency with SQLite**: blobs are immutable. Create = persist the secret first, then commit the DB reference (compensating delete on DB failure). Update = persist a new entry, swap the reference in one transaction, then delete the old entry. Delete = DB row first, vault entry second. `Put` reports success only after the new vault file is durably in place, so the database can never reference an unpersisted secret; cleanup failures leave identifiable orphans, collected by a garbage sweep that only removes unreferenced entries older than 24 hours (the age gate covers the crash window between a durable Put and its DB commit; references shared by several rows are live and untouchable).
- **Shared-reference deletion contract (binding on any future caller)**: the vault API has NO unconditional delete. Compensation uses `DeleteCompensating`, which only ever applies to a reference that is still pending (created by this process, never committed) and therefore cannot be referenced or shared. All business cleanup uses `DeleteIfUnreferenced`, whose live-reference check runs under the vault lock at decision time. Any future service that creates or drops references must serialize those DB mutations together with these cleanup calls under one service-level mutex, making check-and-delete atomic with respect to reference changes; the single-instance lock excludes other processes.
- **Scope note (PR #9 cleanup)**: the Stage 4A `ProxyService` and its UI were removed by project-owner decision. The vault itself, its file format and all existing entries and references are retained unchanged as a data-compatibility layer: `main` still opens the vault at startup (preserving the recovery behaviour below), but no current product feature reads or writes credentials through a user-facing service, and there is no Vault sidebar entry.

- **Atomicity and recovery (Windows)**: every write goes temp file → fsync → permission restriction → snapshot of the previous good file to `secrets.vault.bak` → `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING|WRITE_THROUGH` (plain `os.Rename` replace semantics are not assumed on Windows) → post-write verification read. A corrupt main file falls back to the backup; if both are corrupt they are quarantined by rename (never deleted) and the store starts empty with every reference resolving to "credential unavailable".
- **File permissions**: the vault and its backup carry a protected DACL granting full access to exactly the current user, Local SYSTEM and Administrators — applied to the file itself via SDDL (`D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<user SID>)`), severing inheritance from the portable folder, and verified by reading the descriptor back on every open. If permissions cannot be tightened, the store refuses to open or write rather than continue quietly. Any future credential-bearing file (for example a proxy core's controller secret, if proxy capability is ever re-introduced) must receive the same `secrets.RestrictFile` treatment.

## Proxy capability (removed from product scope)

Proxy management, subscription import, the unified proxy configuration and any proxy core runtime were removed from the product scope in the PR #9 cleanup (project-owner decision) and are not current or scheduled functionality. The 「代理配置」 sidebar entry is a placeholder page only. Whether proxy capability is ever re-introduced will be evaluated separately in the future; it is not on the roadmap. (One design constraint is recorded for such an evaluation, so it is not lost: a proxied instance must be considered "ready" only when the proxy core itself confirms it through its controller — a successful TCP connection to a listener port is not sufficient evidence — and a not-ready proxied instance must fail closed, never fall back to a direct connection. None of that exists in the current code.)

## Logging and diagnostics (Stage 5B, internal/logging)

Three categorized JSON Lines streams live in `data/logs/`, each in dated files (`<category>-YYYY-MM-DD.log`, rolling to `.002`, `.003`, … volumes at 5 MB):

- **run** — application lifecycle and runtime state (the existing `*slog.Logger`, through a sanitizing guard handler); retention 30 days, 20 MB total.
- **operation** — the audit trail of user-initiated business mutations (instance create, update, delete, theme change, diagnostic export). Records are a fixed field whitelist by construction (operation, target type/ID, result, duration, safe error class) — no request data, credentials or free-form user text can enter them; services attach the logging system through an exported `Auditor` field wired once in `main`.
- **error** — error-level records, tee'd from the run stream by the same guard handler; retention 90 days, 50 MB total (operation logs: also 90 days / 50 MB).

The guard handler drops credential-named attributes outright and scrubs error values (URL userinfo, key=value secrets, long token-like runs), so the safety does not depend on call sites remembering what not to log. Retention/capacity enforcement runs at startup, on roll-over and periodically; it only ever touches the category's own files, never the file currently being written, and a cleanup failure is recorded for diagnostics instead of failing startup.

The data management page (「数据管理」, the single sidebar entry that now hosts logs, operation audit and diagnostics) shows the data directory, database state and size, instance count, app version and per-category log statistics, and offers the exports (`DiagnosticsService`): a ZIP with `manifest.json` (per-file SHA-256, format version), `acceptance-record.json` (version/schema/platform/status/retention state) and the three log streams — nothing else. Every exported file passes a sensitivity scan first; a hit aborts the export. The destination is chosen through the native save dialog (wired in `internal/app`, keeping the service layer GUI-free), the archive is written to a temp file and renamed into place, and no absolute machine paths are recorded in the export metadata.

## Removed proxy / subscription / Mihomo features (PR #9 scope cleanup)

The following Stage 4A / 6 / 6C product features were removed by project-owner decision and no longer exist in the code: proxy server CRUD (`ProxyService`) and its page; subscription management, the SSRF-guarded subscription fetcher (including the Fake-IP system-proxy fallback) and the import pipeline (`SubscriptionService`, `internal/mihomoimport`); the unified 「代理配置」 page (replaced by a placeholder that only states the feature is not yet open and calls no service); and the Mihomo core runtime (`internal/mihomocore`, `CoreService`, the settings 「Mihomo 内核」 section, and any bundling of a core binary — the build artifact is the application executable only, and the app neither downloads, installs nor starts a core at startup, nor stops one at exit).

Data compatibility is deliberately preserved: the historical tables (`proxies`, `subscriptions`, `mihomo_configs`, `mihomo_proxy_groups`, `mihomo_proxy_group_members`) and all their rows stay in existing databases, migrations 0001–0009 are untouched, and the `internal/model` types for those tables remain as the historical data model. The store layer was converged to the minimum compatibility surface in the final review round: no proxy/subscription/config create, update or delete methods remain — only the vault reference queries (`SecretRefInUse`, `AllSecretRefs`) still read those tables, so guarded vault cleanup keeps recognising historical credential refs. Instance records keep their stored `proxy_id` value as data, but it is no longer a binding: the instance page shows no proxy column or selector, `InstanceService` exposes no proxy list, creation always writes `proxy_id` NULL, and updates preserve the stored value verbatim. The credential vault file and its entries are likewise untouched. Nothing in this cleanup deletes user data.

The diagnostics fault report was cleaned at the same time: it carries only generic application / database / instance summary state — no core state or log, no subscription refresh state and no proxy configuration fields — and remains fail-closed scanned and path-redacted.

## Security notes

- CDP debugging ports are never exposed publicly; they bind to localhost only (Stage 9).
- The frontend cannot execute arbitrary commands; it can only call the explicitly registered service methods.
- Secrets (credentials, subscription URLs, private proxy configuration) are never stored in SQLite in plain committed files and never enter this repository — see `docs/DATABASE.md` and `.gitignore`.

## Deliberately excluded

Electron, Docker, Redis, MongoDB, GraphQL and microservices are out of scope (AGENTS.md section 3). The scaffold's mobile and Docker assets are not part of this project; the only supported target is Windows 11 x64.
