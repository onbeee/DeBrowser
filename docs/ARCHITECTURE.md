# DeBrowser 架构

本文档说明 DeBrowser 当前的系统架构、模块职责与运行机制。数据库结构见 [DATABASE.md](DATABASE.md)，功能与交付状态见 [ROADMAP.md](ROADMAP.md)，开发流程见 [DEVELOPMENT.md](DEVELOPMENT.md)。

## 架构概览

DeBrowser 是模块化单体：一个 Go 二进制内嵌一个 React 前端，通过 Wails v3 以原生 Windows 桌面应用交付。没有微服务，没有外部服务器，全部状态保存在用户自己的机器上。

```text
┌────────────────────────────────────────────────────────┐
│ React 前端 (frontend/)                                 │
│  七个页面 · 布局组件 · Zustand 界面/通知 store         │
└──────────────┬─────────────────────────────────────────┘
               │ 生成的 bindings + 类型化事件 (app:status)
┌──────────────▼─────────────────────────────────────────┐
│ Wails v3 应用 (internal/app)                           │
├────────────────────────────────────────────────────────┤
│ 服务层 (internal/service)                              │
│  AppService · InstanceService · BrowserService         │
│  BookmarkService · SyncService · ProxyService          │
│  DiagnosticsService                                    │
├────────────────────────────────────────────────────────┤
│ 基础层 (internal/)                                     │
│  paths · config · settings · logging · database        │
│  model · store · runner · cdp · capture · winmgr       │
│  chromebookmarks · mihomo · secrets · singleinstance   │
│  pfiles · safedelete · lifecycle · version             │
├────────────────────────────────────────────────────────┤
│ 本地资源（便携目录，见「数据目录」）                   │
│  data/debrowser.db · data/profiles/ · data/logs/       │
│  data/mihomo/ · data/secrets.vault · config/settings.json │
└────────────────────────────────────────────────────────┘
```

职责划分：Go 负责浏览器进程管理、实例生命周期、Profile 隔离、浏览器登记、书签数据、多开同步、代理核心管理、数据库与日志；React 只负责渲染、交互、表单、表格、前端状态与通知。

## 技术组成

Go 1.26 + Wails v3.0.0 后端；React 18 + TypeScript + Vite + Tailwind CSS v4 前端；SQLite（modernc.org/sqlite，纯 Go 驱动）存储；浏览器控制使用 Chrome DevTools Protocol（CDP）；代理核心为 Mihomo（运行时下载，见「代理运行机制」）。版本明细见 [README.md](../README.md) 的技术栈表。

## 应用启动与关闭流程

`main.go` 的启动顺序固定：

1. `config`/`paths` 从可执行文件所在目录解析便携布局，创建全部目录并探测可写性；不可写时明确报错中止，永不回退到 `%AppData%`。启动是直接的：没有欢迎页或选择页，也不从任何其他位置扫描、检测或导入数据。
2. `logging` 打开日志系统（在数据库与服务之前打开，关闭时最后关闭）。
3. `singleinstance` 取得按安装划分的操作系统级文件锁（`data/app.lock`）。锁由操作系统仲裁并在持有者以任何方式退出时自动释放，不存在陈旧锁；第二次启动只写入激活信号（`data/activate.request`）请已运行实例聚焦窗口，然后在不触碰数据库的情况下退出。
4. `database` 打开 SQLite 并以事务方式应用待执行迁移（升级前先做经验证的备份，见 [DATABASE.md](DATABASE.md)）。
5. `service` 依次构建服务：AppService（加载设置并应用日志容量）→ InstanceService（构造时对账运行身份记录，见「浏览器实例和进程管理」）→ BrowserService → BookmarkService → 打开凭据 Vault → DiagnosticsService → SyncService → ProxyService（并把实例启动时的代理端口查询钩子接线到 InstanceService）。
6. `app` 组装 Wails 应用并运行。后台循环（状态事件每 10 秒、激活信号监视每 500 毫秒）由 `lifecycle` 在应用 context 下治理。

关闭时按固定顺序释放：应用停止并排空后台循环 → 代理服务停掉自有 Mihomo 核心 → 数据库 → 实例锁 → 日志。

## 前后端通信

- **Bindings**：Go 服务的导出方法经静态生成的 TypeScript bindings 暴露给前端（`wails3 generate bindings` 重新生成；CI 校验已提交的 bindings 与生成结果一致）。当前共 **7 个服务、62 个方法**。前端只能调用明确注册的服务方法，不能执行任意命令。原生文件对话框（登记浏览器、导入代理配置、日志导出保存位置）由 `internal/app` 接线，服务层不依赖 GUI。
- **事件**：目前只有一个类型化事件 `app:status`（应用状态，每 10 秒发出，也可经 `AppService.GetStatus()` 按需获取）。
- **前端状态**：Zustand 应用 store 保存当前页面、后端状态与主题；通知另有独立的通知 store；页面级状态留在各页面内。每次用户操作由前端生成唯一的 `operation_id` 并作为 bindings 调用的第一个参数传入，贯穿该操作的全部日志记录（见「日志系统」）。

## 后端服务与模块职责

| 服务 | 职责 |
| --- | --- |
| `AppService` | 应用状态与用户设置（主题、日志容量），设置存 `config/settings.json` |
| `InstanceService` | 实例 CRUD、实例文件分配/重命名/换绑、浏览器进程启动/关闭/监控与重启对账 |
| `BrowserService` | 浏览器登记（纯路径）与实例的内核关联解析 |
| `BookmarkService` | 书签资源库与实例真实书签的分发、聚合搜索、编辑与删除 |
| `SyncService` | 多开同步会话（主控—跟随）、窗口排列与镜像 |

| `DiagnosticsService` | 数据管理页后端：应用版本、数据库状态、统一日志查看与导出（名字沿用自早期的诊断功能；早期的一键诊断导出已移除，统一日志是唯一的记录系统） |

## 浏览器实例和进程管理

### 浏览器登记

手动登记是**纯路径登记**：用户在文件选择器中任选一个程序可执行文件，`BrowserService` 只把绝对路径与从文件名派生的显示名存入 `external_browsers`。不做任何身份、产品、版本、签名、发布者或存在性检查，不要求是 Chrome 或 Brave；登记本身永不启动、复制、移动、修改或删除该程序，永不读取它的 Profile。同一路径重复登记返回既有记录；移除登记只删除数据库行，被实例引用的登记禁止移除（不级联影响实例）。

实例按登记的稳定 ID 关联（`kernel_id`），可执行路径不落库、由服务按 ID 实时解析，登记改路径即时生效；关联时的名称保存为快照（`kernel_name`）用于显示。

### 启动、关闭与进程身份

- **启动**：服务按实例关联实时解析可执行路径，校验实例文件是 `data/profiles/` 下的受管文件夹（缺失时补建空目录；无法证明位于受管根内时拒绝启动），以 `--user-data-dir=<实例文件绝对路径>` 启动进程，并分配仅回环的 CDP 调试端口（`--remote-debugging-address=127.0.0.1`）。实例绑定了代理节点时，另按「代理运行机制」的规则处理。进程存活过稳定窗口且身份核验全部通过后，才写入身份记录（`instance_runtime` 表）、置为运行中并开始监控。
- **身份核验**：PID + 进程创建时间 + 可执行路径 + 命令行，四项共同核验；命令行经严格参数解析，`--user-data-dir` 的值必须与实例文件完整路径精确相等（子串或前缀相同不算一致）。任一信号缺失或不可读一律视为核验失败，绝不猜测。
- **关闭**：只对已核验的被跟踪进程投递优雅关闭（Windows 的 `WM_CLOSE`，等同用户点击关闭按钮）；从不按进程名全局结束进程，从不强制结束进程树。限定时间内未退出则如实报告「关闭未完成」，实例保持运行中。
- **退出感知**：每个被跟踪进程都有监控协程；用户直接关闭浏览器窗口或浏览器崩溃都会被感知，身份记录随之删除，状态按退出码更新为已关闭或错误。
- **重启恢复**：DeBrowser 退出不关闭浏览器。下次启动时按身份记录逐项重新核验：通过的重新接管监控；证明已失效的清除并置为已关闭；进程仍在但身份无法确认的，实例进入「无法确认」状态并冻结一切可能危及数据的操作（启动、关闭、删除、重命名/更换实例文件），只保留无风险的查看与名称、内核关联修改，留待后续对账重新判定。核验失败且无法确认本次启动的进程已退出时，同样写入身份记录进入「无法确认」，绝不冒充普通失败。

## Profile 隔离机制

每个实例绑定一个实例文件：`data/profiles/` 下的文件夹，浏览器以它为 `--user-data-dir` 运行。一对一绑定由数据库 UNIQUE 约束与服务检查共同保证，运行中的实例之间永不共享。

- 新建：默认（持久计数器顺序编号 P-1、P-2……，只增不减、永不复用）、自定（新建文件夹）、选择（绑定保留的未绑定文件夹，不复制内容）。
- 编辑：重命名当前文件夹（数据随文件夹移动），或更换绑定（原文件夹解除绑定并保留在磁盘上）。
- 删除实例默认只删除数据库记录、保留实例文件；只有用户明确选择「删除实例及实例文件」时才删除文件夹（保护规则见「安全与隐私边界」）。

浏览器实际使用的 Profile 目录是用户数据目录下的一个子目录（如 `Default`、`Profile 1`），不是用户数据目录本身；书签等按 Profile 读取的功能统一经 `chromebookmarks.ResolveProfileDir` 解析（见「书签管理机制」）。

## 代理运行机制

代理模块由 `ProxyService` 与 `internal/mihomo` 实现，只使用 Mihomo 的原生能力，DeBrowser 不实现代理引擎、规则引擎或 DNS：

- **核心管理**：Mihomo v1.19.34 不随应用打包。首次启动核心时，从官方 GitHub 发布下载对应平台的发行包，先校验压缩包 SHA-256、再校验解压出的可执行文件 SHA-256，双重校验通过后安装到 `data/mihomo/`。核心只以 DeBrowser 自己启动的子进程方式运行（Windows 下加入 Job Object，应用退出时一并结束，不留孤儿进程）；控制器只监听 `127.0.0.1:19097` 并使用随机密钥（保存在 `data/mihomo/` 内）；控制器端口被占用时明确报错，绝不接管其他程序的进程。DeBrowser 不影响用户自行安装的 Clash/Mihomo。
- **节点来源**：订阅（下载内容并解析）与本地 Clash/Mihomo YAML 文件（导入时在 `data/mihomo/sources/` 保存 DeBrowser 自己的副本）两种来源，导入时统一解析顶层节点列表存入数据库；节点的完整定义以原文保存，生成核心配置时不再回读来源。订阅地址只存入凭据 Vault。订阅可刷新（失败保留旧节点）；本地来源的更新是重新选择文件、先完整解析成功才替换。删除来源时其节点与相关实例绑定一并级联删除。
- **实例绑定**：绑定关系只有一份（`instance_proxy_bindings` 表），代理页面与实例编辑表单共用。每个绑定在创建时从 21001 起分配一个最低空闲的本地监听端口，绑定生命周期内保持不变。核心配置由数据库生成：全部节点加每绑定一条 loopback 监听，监听通过 Mihomo 的 `proxy:` 直绑字段直达所选节点——没有规则、规则集、代理组或运行模式。
- **启动门禁**：实例启动时经钩子查询绑定：无绑定则直连；有绑定且核心运行、对应监听经握手确认可用时，追加 `--proxy-server=http://127.0.0.1:<port>`；有绑定但核心未运行或监听不可用时，明确报错拒绝启动，绝不静默直连。核心运行期间修改绑定会重新生成配置并热重载，失败时如实报错（修改已保存，重启核心后生效），不回滚数据。
- **测速**：手动触发，使用核心原生的节点延迟接口对全部节点逐个实际连接测试（固定测试目标、单节点超时 5 秒、有限并发），结果只显示不落库。

## 书签管理机制

书签有两套完全独立的数据：DeBrowser 资源库（SQLite `bookmark_nodes` 树，见 [DATABASE.md](DATABASE.md)）与各实例实际 Profile 目录下的 Chromium 原生 `Bookmarks` 文件。资源库的编辑、删除不自动影响任何实例；实例书签的修改不回写资源库；分发只通过同步操作显式进行。

- **Profile 目录解析**：实际 Profile 目录统一由 `chromebookmarks.ResolveProfileDir` 解析：优先读取用户数据目录下 `Local State` 的 `profile.last_used`（必须是安全的单一相对目录名，目标目录必须存在，否则明确失败，不回退、不扫描其他 Profile）；`Local State` 不存在或没有有效的最近使用记录时，仅在 `Default` 目录存在时回退到 `Default`；`Local State` 已损坏则明确失败。
- **空书签处理**：Profile 目录是否有效与其中是否存在 `Bookmarks` 文件无关：浏览器首次启动后、用户尚未添加任何书签时，该文件合法地不存在，此时书签为空集合。所有书签入口（数量统计、同步、搜索、编辑、删除）共用同一解析结果。
- **文件读写**：`internal/chromebookmarks` 把 `Bookmarks` 文档作为解码后的 JSON 结构整体处理，完整保留根节点、节点 ID/GUID、时间字段与未知字段，数字以原始文本精度保留。文件不存在按空书签处理（读取为空集合），写入时创建符合 Chromium 结构的合法文件；文件存在但无法解析或结构不符合 Chromium 书签格式时明确报错，绝不把损坏文件当成空书签静默覆盖；绝不猜测其他浏览器的数据格式（不支持 Firefox 等非 Chromium 书签存储）。
- **运行状态保护**：读写任何实例的书签文件之前，必须经运行时生效状态确认该实例已停止（不只看数据库落库状态）；运行中与无法确认状态一律禁止读写，批量操作逐实例独立判定、跳过并反馈原因。书签管理页面的「同步」入口会先检查全部实例：存在运行中实例时，由用户确认后调用既有正常关闭流程关闭全部实例并复查确认停止，才打开同步弹窗；后端在每次实际读写前仍独立复核目标实例状态。
- **写入安全**：同一 Profile 的书签操作互斥串行；写入走同目录临时文件 → 校验 → 原子替换 → 重新读取并完整验证；替换前把原文件保存为单个滚动恢复副本 `Bookmarks.debwbak`。替换后验证失败时自动用恢复副本还原原文件，并区分「已恢复」与「恢复失败」如实报错；任何失败都不假报成功。
- **分发规则**：同步把资源库所选节点（文件夹含全部子树、保留层级）写入目标实例的书签栏；同一目标文件夹内 URL 相同视为已存在并跳过，同名文件夹复用不重建，只增不删。
- **聚合搜索**：跨实例聚合搜索只查已确认停止且可读的实例，结果只呈现名称、网址与不同实例数量，不暴露实例名称或明细；精确目标（实例、根节点、节点 ID、父级路径与内容快照）只保存在后端短期会话中，执行时重新核对实例状态、重新读取文件并按节点 ID 与路径复核后才修改。

## 多开同步机制

多开同步由 `SyncService` 实现：一个主控实例、多个跟随实例，会话期间同步以下内容：

- **标签页生命周期与导航**：主控实例的标签创建、关闭、切换，以及已提交的导航与刷新，经每实例独立的回环 CDP 连接同步到跟随实例。页面事件由隔离执行环境中的观察脚本（`internal/capture`）捕获、经 CDP 客户端（`internal/cdp`）传递，再以 CDP 输入在跟随实例执行。浏览器原生界面无法经 CDP 确认的效果不做模拟：只有 CDP 能确认的效果才会被同步。
- **窗口排列与镜像**：经原生窗口管理（`internal/winmgr`）调整窗口几何（不激活窗口）；开始同步时先建立主窗口几何基线，排列/恢复窗口与镜像互斥执行且完成后刷新基线，暂停期间不执行镜像。
- **会话治理**：支持开始、暂停、恢复、停止；跟随实例逐个隔离，单个跟随实例故障不影响其他实例与主控；恢复同步在系统暂停原因未消失时如实返回暂停原因。

## 日志系统

统一自动记录系统（`internal/logging`）是唯一的记录系统，不存在第二套审计或诊断通道。三条 JSONL 流存放在 `data/logs/`（按日期命名、5 MB 分卷）：

- **运行记录**（保留 30 天）：应用生命周期、页面打开/离开、后台循环与结构化运行日志。
- **操作记录**（保留 90 天）：用户发起的业务操作及其步骤与结果。
- **错误记录**（保留 90 天）：错误级日志与每次失败操作的完整错误事件（含用户实际看到的提示）。

记录采用统一事件模型，以 `operation_id` 关联一次操作的全部事件。三条流共用一个用户可配置的总容量上限（默认 100 MB，存 `config/settings.json`），超出时先整文件删除最旧的已轮转文件，再按完整操作组修剪当前文件，最新一条记录永不删除。记录落盘前统一清洗：凭据类字段整体丢弃，自由文本脱敏；写入失败只累计计数，永不使业务操作失败。数据管理页可按类别与日期范围导出 ZIP（逐文件 SHA-256 清单、导出前敏感性扫描、命中即中止、路径脱敏），供用户把日志提供给开发者定位问题。

前端通知与日志相互独立：通知只存在于内存中（通知台最近 80 条，重点通知同时浮窗提醒），负责即时展示；日志负责长期记录与导出。

## 安全与隐私边界

- **Profile 隔离**：实例文件互不共享；活动 Profile 永不在浏览器使用期间被复制。DeBrowser 不宣称指纹隔离。
- **实例文件删除保护**：「删除实例及实例文件」是显式破坏性路径：拒绝删除运行中的实例、拒绝 profiles 根目录本身、拒绝任何无法证明严格位于 `data/profiles/` 内的目标（符号链接与每个路径组件都必须解析到受管根内）。删除以经验证的文件系统**对象**为锚（`internal/pfiles` 先移入隔离槽、数据库记录删除成功后才由 `internal/safedelete` 擦除），不以路径字符串做裸递归删除；平台无法提供对象锚定保证时失败关闭（拒绝并保留数据）。
- **进程操作边界**：只操作 DeBrowser 自己启动并核验过的浏览器进程与自己启动的 Mihomo 核心进程；身份无法确认时宁可冻结，也不误关、误删。
- **凭据 Vault**：`internal/secrets` 保存凭据（`data/secrets.vault`，Windows DPAPI CurrentUser 保护；SQLite 只存不透明 `secret_ref`，明文永不进入数据库、日志与设置）。当前由代理模块用于保存订阅地址；历史功能写入的条目同样保留。条目在仍被引用时永不回收，删除只有「未被引用才删」的受守卫形式，没有无条件删除。DPAPI 的跨机器限制见 [README.md](../README.md)。
- **记录边界**：永不记录 Cookie、密码、Token、Vault 明文、浏览器历史或网页内容；CDP 与代理监听、代理控制器都只绑定回环地址。
